# Yeti deployment implementation plan

Goal: serve Kittakat and its persistent database from Yeti at the approved DuckDNS domain.
Spec: ../specs/2026-11-01-yeti-design.md

1. Add tests for native SQLite persistence, migration replay/checksum protection, atomic rollback, concurrent batches and recovery. Run them failing before adding `lib/server/sqlite.ts`. Reuse the ledger service against the real adapter.
2. Add a Node environment shim and Next standalone build configuration while preserving the Worker path. Build, run the full suite and run existing integration tests against a disposable local database.
3. Provision the approved Node layer and temporary SSH key. Deploy immutable source/build release with a separate private database directory. Apply pending migrations, configure process supervision and daily validated SQLite backups.
4. Connect DuckDNS only after origin checks succeed. Configure trusted HTTPS and renewal. Verify live login/bootstrap, persistence after process restart, database integrity, restored backup and browser rendering. Remove temporary SSH access and deliver the operating instructions.

Review focus: failed migrations must leave no partial schema; batches must not yield inside SQLite transactions; deployments must never overwrite persistent records; forged identity/IP headers must not bypass authentication/throttling; HTTPS must set Secure session cookies and preserve same-origin checks.
